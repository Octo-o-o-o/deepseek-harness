# Agent Note: 用 ArrowUp 召回本会话发过的提问

Status: implemented

[English](2026-08-14-composer-prompt-recall.md) | 中文

## 问题

输入框没有任何回到"已经发出去那句"的路径。想改一个词重发一遍，就得滚动 transcript、选中文字、复制回来——而这个动作，每个 shell、每个 REPL 都用 ArrowUp 解决。这两个键此前只在一个很窄的情形下被占用（触发菜单打开时用它们移动高亮），其余情况直接落到原生光标移动。

## 决策

光标塌缩在 offset 0 时按 ArrowUp，开始一次对本会话自己发过的提问的召回，从新到旧；ArrowDown 向新的方向走，越过最新一条后恢复召回开始时暂存的草稿。触发菜单对这两个键仍有优先认领权——只有 `arbitrate` 把按键交回来，它们才表示召回。

召回一旦开始，光标就不再参与判断。另一种做法——每次按键都重新检查 offset 0——会卡在被召回的文本自身上：召回把光标放在末尾以便立即编辑，于是多行提问会把下一次 ArrowUp 当成普通的换行移动吸收掉。因此改由显式动作结束召回：编辑草稿、发送，或切换会话。停在最旧一条不再回绕，这既是 shell 的行为，也是长按该键仍然安全的原因。

`prompt-history.ts` 是纯的——一个从对话节点出发的推导，加一个游标转移；输入框在 ref 中持有游标，读取本次召回的草稿，再经普通的 `setDraft` 路径加一次 `track` 写入，与 space 认领手势完全一致。冻结的输入契约未被触碰：召回是组合既有动词，而不是新增机器状态。

历史来自已加载的对话节点，而不是另一份列表。steering 消息计入，因为那也是用户敲的；纯空白与纯图片的提问被丢弃，因为它们召回不出东西；前后相邻的重复提问会合并，这样长按 ArrowUp 穿过一次重试时仍在前进。

## 考虑过的替代方案

**在本浏览器标签页内维护一个已提交草稿的环形缓冲。** 它撑不过一次刷新，也遗忘标签页打开之前发过的一切，并且会在屏幕上已有的 transcript 之外再造一个事实来源。

**在 `$DSH_HOME` 下做跨会话的持久提问历史。** 那是个更大的特性，自带隐私问题（提问是本产品里最敏感的文本），且当前没有任何消费者提出这个需求。在出现之前，已加载窗口是诚实的边界。

**把游标放进机器状态而不是组件 ref。** 该游标在同一次 keydown 内被读写，且从不参与渲染；把它加进 `InputState` 等于为一个无人观察的值去拓宽一个冻结契约。

## 影响

已加载窗口决定召回能回溯多远——滚出加载范围的旧提问无法召回，这与用户能看到的范围一致。输入框只读或处于 pending lock 时拒绝召回，与其他所有草稿写入所处的只读区间相同。覆盖为：`prompt-history.client.spec.ts` 覆盖纯推导与游标，`input-bar.client.spec.tsx` 中的 `prompt recall` 用例覆盖按键路径、触发菜单优先级、输入法保护，以及两种拒绝。
